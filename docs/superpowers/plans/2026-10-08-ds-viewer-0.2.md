# `@krapwoo/ds-viewer` 0.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the kit moved into the package with per-component and standalone catalog pages, the two carried-over console errors fixed, new-project `init`, the logo config/plumbing with its now-approved sidebar visual, `native-preview/` retired in favor of the repo viewing its own starter kit with `ds-viewer dev`, and a CI browser smoke test — the "0.2" row of the approved design's §6 "Releases" table, so the owner's new app can use the package.

**Architecture:** `native/components/`, `tokens/`, `icons/`, and `WHEN_TO_USE.md` move to `starter-kit/` (`git mv`, history kept) and every one of today's 47 `CatalogExample.tsx`/`CatalogFrameworkExample.tsx` sections becomes its own `defineCatalogPage()` file, either next to its component (`starter-kit/components/<Name>/<Export>.catalog.tsx`) or standalone (`starter-kit/pages/*.catalog.tsx`). The repository stops depending on a dedicated `native-preview/` Expo shell and instead views the starter kit the same way a real user would: a small sibling `kit-host/` Expo project that depends on `@krapwoo/ds-viewer` via `file:..` and whose `ds-viewer.config.ts` globs reach `../starter-kit/**` — which requires two small CLI fixes (`cli/glob.ts` must resolve a literal `..` path segment; `cli/workspace.ts`'s generated Metro config must watch every configured glob's folder, not just the project root). `cli/init.ts` gains `initNewProject` (preflight → install missing `react-native-svg`/`react-native-safe-area-context` via an injectable installer → copy the bundled kit into `src/ds/` → write config with `starterKit.version`) alongside the existing `initExistingProject`. A CI job runs Puppeteer headlessly against `kit-host`'s `dev` output and fails if any of the 47 kit pages (or the repo's own 18 "Viewer" documentation pages) logs a console error.

**Tech Stack:** Same as 0.1 — TypeScript (compiled with `tsc`), Node's built-in test runner with `--experimental-strip-types`, Expo SDK 57, React Native 0.86, React Native Web 0.21. New for 0.2: Puppeteer (headless Chromium, for the CI browser smoke test).

**Spec:** `docs/superpowers/specs/2026-10-07-ds-viewer-npm-package-design.md` (revision 3) — 0.2 row of §6 "Releases": *"Kit moved into the package with component and standalone pages, kit console errors fixed (`Icon.native`, `Loading`), new-project `init`, logo in the sidebar header (mockup first), `native-preview/` retired, `@krapwoo/catalog` deprecation (owner approval)"* — plus every section it depends on (§1 "This repository after the change", §1 "Host requirements", §2 `init`'s new-project column and steps 3–4, §2 Config `logo`/`starterKit`, §2 "Pages and discovery", §3 "`@krapwoo/ds-viewer/generated`", §6 "Browser smoke test in CI ... ## Global Constraints

- Package name `@krapwoo/ds-viewer`; command `ds-viewer`. `main` (0.1.1, commit `04fea63`) is the base for this plan; nothing below reopens 0.1 scope.
- `npm test` is 98 tests today. The CLI's props/sync tests need a sibling project's `node_modules` for `@types/react`/`react-native` type roots; CI runs that sibling's `npm ci` before `npm test`. 0.2 moves this role from `native-preview/` to `kit-host/` — every reference to `native-preview` in test files, `tsconfig.json`, and CI workflows is updated, not left dangling (Task 5).
- Root `.npmrc` has `legacy-peer-deps=true`: do not remove it. `kit-host/`'s own `npm install` inherits it (npm reads `.npmrc` from every ancestor directory up to the repo root), which is what keeps `@krapwoo/ds-viewer`'s `react`/`react-native`/etc. peer dependencies from being auto-installed a second time under `kit-host/node_modules/@krapwoo/ds-viewer/node_modules/` — exactly one React in the bundle, the same reasoning the 0.1 plan recorded for the root install.
- The starter kit's fixed internal layout is `<kit root>/components`, `<kit root>/tokens`, `<kit root>/icons`, `<kit root>/pages`, `<kit root>/WHEN_TO_USE.md` (design §1). Only the kit root itself is configurable (`init`'s `--kit-root`, default `src/ds`).
- The kit version equals the package version (design §1) — `starterKit.version` is always `init`'s own installed version, the same `ownVersion()`/`packageRoot()` lookup `cli/init.ts` already uses for the devDependency entry.
- Every kit page (and every repo-only "Viewer" documentation page) renders with zero `console.error` and no uncaught errors (design Decisions, "Starter-kit quality"). A kit-caused deprecation warning is fixed only when the fix is local to kit code; the `useNativeDriver` web warning (Banner) is report-only, same as the design's known-issues list.
- `sync`, `dev`, and `init` read nothing from the project except via the TypeScript compiler and the sandboxed config loader (design §3) — unchanged from 0.1; nothing in this plan executes app code from Node.
- One broken component/page/token file never stops the rest of a `sync`/`init`/kit-copy run — it is reported with its file (design, Error-handling rule) — unchanged from 0.1; every new file-walking function below follows the same per-entry try/catch shape as `cli/sync.ts`'s existing loops.
- `init` never overwrites a file that already exists, whether that file is `ds-viewer.config.ts`, a draft `.catalog.tsx`, or (new in 0.2) a file inside the copied starter kit. Re-running `init` only adds what is missing.
- Tests never run a real `expo install` or a real interactive prompt: `initNewProject`'s installer and `initExistingProject`'s confirm function are both injectable, and the existing non-interactive-stdin handling is extended, not replaced.
- GitHub Actions stay SHA-pinned (design §4 "GitHub Action", §5 "Releasing"). This plan introduces no new GitHub Action — the browser smoke test (Task 10) is one new npm devDependency plus a step in the existing, already-pinned `ci.yml` job, so no new SHA needs resolving.
- Commits, pushes, and any publish step each need separate authorization. Commit steps below run only when commit authority is granted. This plan never runs `npm publish`, never creates a release tag, and never deprecates `@krapwoo/catalog` — all three are owner-only (spec §5, "Owner actions"; brief "Not workers' work").
- Every "RED step" (`Run it and confirm it fails`) quotes the expected failure the same way the 0.1 plan's did: Node reports the *resolved absolute path*, not the bare relative specifier written in the importing file — confirm the run fails with a "module not found" error, not that the quoted string appears verbatim.

### Task 1: `resolveGlob` resolves a literal `..`/`.` path segment

**Files:**
- Modify: `cli/glob.ts`
- Modify: `cli/__tests__/glob.test.ts`

**Interfaces:**
- Consumes: none new.
- Produces: `resolveGlob(root: string, pattern: string): string[]` — same signature, now also correct for a pattern containing a literal `..` or `.` segment (e.g. `'../starter-kit/components/*/index.ts'`, needed by `kit-host`'s config in Task 5).

Confirmed by spike (`spikes/README.md` "glob-dotdot"): `walk()`'s per-segment branch treats every non-`**` segment as a regex matched against `readdirSync(dir)`'s entries. `readdirSync` never returns `.`/`..` as entries, so a pattern like `../starter-kit/components/*/index.ts` resolves to `[]` today — silently, with no error — which would make `kit-host`'s `sync` report 0 components. The fix: before touching the filesystem, recognize a literal `.`/`..` segment and simply advance `consumed` by it (exactly what `path.join` already does correctly for every *other* caller of `resolveGlob`'s result).

- [ ] **Step 1: Write the failing test** — add to `cli/__tests__/glob.test.ts`:

```ts
test('resolveGlob resolves a pattern that climbs out of root with ".."', () => {
  const root = makeFixture();
  const parent = path.dirname(root);
  const siblingName = path.basename(root);
  const matches = resolveGlob(path.join(root, 'src'), `../../${siblingName}/src/tokens/index.ts`).sort();
  assert.deepEqual(matches, [path.join(root, 'src/tokens/index.ts')]);
  rmSync(root, { recursive: true, force: true });
});

test('resolveGlob treats a leading "." segment as the root itself', () => {
  const root = makeFixture();
  assert.deepEqual(resolveGlob(root, './src/tokens/index.ts'), [path.join(root, 'src/tokens/index.ts')]);
  rmSync(root, { recursive: true, force: true });
});
```

— `common.key` is set, then `common` is spread onto `<Path {...common} .../>` etc.; React requires `key` to be passed directly, not through a spread.

```
[error] React does not recognize the `translateX` prop on a DOM element.
```

— confirmed by reading `react-native-svg@15.15.4`'s web shim (`lib/commonjs/web/utils/prepare.js`): on web, `prepare()` destructures out `transform`/`origin`/`style`/etc. before spreading the rest onto the DOM node, but does **not** destructure `translateX`/`translateY` — those two remain in `rest` and reach the DOM verbatim, even though `parseTransformProp` *also* correctly folds them into the computed `transform` attribute elsewhere in the same function. The fix is to never pass `translateX`/`translateY` as props at all — build the equivalent `transform` string ourselves, which the library handles correctly on both platforms (confirmed by reading `lib/commonjs/lib/extract/extractTransform.js`'s `transformToMatrix`, which parses a `transform` string the same way natively).

#### `Manifest.catalog.tsx`: reads generated data, not `buildComponentManifest`

Design §1: *"The Manifest page reads `@krapwoo/ds-viewer/generated`."* Today's page calls `buildComponentManifest(sections, groups)` against the hand-assembled, module-scope `sections`/`groups` arrays — both of which stop existing once every page moves to its own file (there is no single array to pass). `buildComponentManifest` itself stays exported from the package unchanged (it's still useful to a 0.1 user who assembled their own `sections`/`groups`, e.g. inside `entry.tsx`'s own scope, which this page cannot reach) — the kit's own Manifest page instead renders the generated `components`/`tokens` JSON directly:

```tsx
import React from 'react';
import { ScrollView, Text, StyleSheet } from 'react-native';
import { defineCatalogPage } from '@krapwoo/ds-viewer';
import { components, tokens } from '@krapwoo/ds-viewer/generated';

const styles = StyleSheet.create({
  box: { maxHeight: 480, overflow: 'hidden' },
  text: { fontSize: 12, fontFamily: 'Menlo', color: '#181818' },
});

function ManifestView() {
  return (
    <ScrollView style={styles.box}>
      <Text selectable style={styles.text}>{JSON.stringify({ components, tokens }, null, 2)}</Text>
    </ScrollView>
  );
}

export default defineCatalogPage({
  group: 'Reference',
  description: 'Every component\'s generated props, and every token module\'s generated values, as plain JSON — built live by `sync` from source, so it can\'t drift out of sync. **The approved rule ("Adaptive"):** no logo → today's name-only header, unchanged. A logo present and its aspect ratio (width ÷ height) is **> 2 → a wordmark**: render only the image (height capped at 28px, left-aligned, `accessibilityLabel`/`alt` set to the app name so it carries the same accessible name text would have — the name is never shown twice), then the caption below it with a bit more top spacing (6px, vs. the normal 2px) to clear the taller image. **≤ 2 → a mark**: a 32×32 image sits beside the name+caption column (12px gap); when the name is longer than 22 characters, the row top-aligns instead of center-aligning, so a wrapping name doesn't float oddly against the small fixed-size mark.   const packageJsonRaw = readFileSync(packageJsonPath, 'utf8');
```

```ts
function defaultInstaller(projectRoot: string, missingPackages: string[]): void {
  if (missingPackages.length === 0) return;

/** Copies every file under `srcDir` into `destDir`, skipping any destination file that already
 *  exists (design's "never overwrites user files" rule — Global Constraints) and reporting, not
 *  throwing on, one unreadable source file (Error-handling rule). Returns every path it wrote. */
function copyKitIfMissing(srcDir: string, destDir: string): string[] {
  const written: string[] = [];
  mkdirSync(destDir, { recursive: true });
  for (const entry of readdirSync(srcDir, { withFileTypes: true })) {
    const srcPath = path.join(srcDir, entry.name);
    const destPath = path.join(destDir, entry.name);
    if (entry.isDirectory()) {
      written.push(...copyKitIfMissing(srcPath, destPath));
      continue;
    }
    if (existsSync(destPath)) continue;
    try {
      copyFileSync(srcPath, destPath);
      written.push(destPath);
    } catch (error) {
      console.warn(`Could not copy ${path.relative(srcDir, srcPath)}: ${(error as Error).message}`);
    }
  }
  return written;
}

    dependencies?: Record<string, string>;
    devDependencies?: Record<string, string>;
  };
  const installedPackages = { ...packageJson.dependencies, ...packageJson.devDependencies };
  const missingKitPackages = KIT_REQUIRED_PACKAGES.filter((name) => !installedPackages[name]);
  await (options.installer ?? defaultInstaller)(projectRoot, missingKitPackages);

  const kitRoot = options.kitRoot ?? 'src/ds';
  const written = copyKitIfMissing(path.join(packageRoot(), 'starter-kit'), path.join(projectRoot, kitRoot));

  const configPath = path.join(projectRoot, 'ds-viewer.config.ts');
  if (!existsSync(configPath)) {
    writeFileSync(configPath, newProjectConfigContents(kitRoot, ownVersion()));
    written.push(configPath);
  }

  written.push(...ensureSharedProjectFiles(projectRoot));

  const messages = [
    ...warnings.map((issue) => `Warning: ${issue.package} not found. Run: ${issue.installCommand}`),
    ...(missingKitPackages.length > 0 ? [`Installed ${missingKitPackages.join(', ')}.`] : []),
    `Copied the starter kit into ${kitRoot}/.`,

  ];
  return { messages, written };
}

/** The one new-vs-existing question (design §2's "One question") — `--new`/`--existing` (wired in

export async function promptInitMode(): Promise<'new' | 'existing' | undefined> {
  if (!process.stdin.isTTY) return undefined;

  const answer = await rl.question('New or existing project? [new/existing] ');
  rl.close();
  const normalized = answer.trim().toLowerCase();

  if (normalized === 'existing' || normalized === 'e') return 'existing';
  return undefined;
}
```

```js
#!/usr/bin/env node
// Drives `ds-viewer dev` as a child process against <projectRoot>, then uses a headless browser to
// visit every page the rendered sidebar links to, failing if any page is missing its heading or
// logged a console error (design §6, "Browser smoke test in CI").
import { spawn } from 'node:child_process';
import puppeteer from 'puppeteer';

const projectRoot = process.argv[2];
if (!projectRoot) {
  console.error('Usage: node scripts/checkCatalogConsole.mjs <projectRoot>');
  process.exit(1);
}

function startDev() {
  return new Promise((resolve, reject) => {
    const child = spawn('npx', ['ds-viewer', 'dev'], { cwd: projectRoot, env: { ...process.env, CI: '1' } });
    let resolved = false;
    const onData = (data) => {
      const text = data.toString();
      process.stdout.write(text);
      const match = text.match(/Starting the catalog at http:\/\/localhost:(\d+)/);
      if (match && !resolved) {
        resolved = true;
        resolve({ child, port: Number(match[1]) });
      }
    };
    child.stdout.on('data', onData);
    child.stderr.on('data', (data) => process.stderr.write(data));
    child.on('exit', (code) => {
      if (!resolved) reject(new Error(`ds-viewer dev exited early with code ${code}`));
    });
    setTimeout(() => {
      if (!resolved) reject(new Error('Timed out waiting for "Starting the catalog at ..." from ds-viewer dev.'));
    }, 60_000);
  });
}

async function main() {
  const { child, port } = await startDev();
  const browser = await puppeteer.launch({ headless: 'new' });
  try {
    const page = await browser.newPage();
    const messages = [];
    page.on('console', (msg) => messages.push({ type: msg.type(), text: msg.text() }));
    page.on('pageerror', (error) => messages.push({ type: 'pageerror', text: String(error) }));

    await page.goto(`http://localhost:${port}`, { waitUntil: 'networkidle0', timeout: 30_000 });
    const ids = await page.evaluate(() => [
      ...new Set([...document.querySelectorAll('a[href^="#"]')].map((a) => a.getAttribute('href').slice(1))),
    ]);
    if (ids.length === 0) throw new Error('No sidebar links found — the catalog may have failed to render at all.');

    const failures = [];
    for (const id of ids) {
      messages.length = 0;
      await page.evaluate((pageId) => {
        window.location.hash = `#${pageId}`;
      }, id);
      await new Promise((resolve) => setTimeout(resolve, 600));
      const hasHeading = await page.evaluate(() => {
        const heading = document.querySelector('[role="heading"]');
        return Boolean(heading && heading.textContent && heading.textContent.trim().length > 0);
      });
      const errors = messages.filter((m) => m.type === 'error' || m.type === 'pageerror');
      if (!hasHeading) failures.push({ id, reason: 'no heading rendered' });
      if (errors.length > 0) failures.push({ id, reason: errors.map((e) => e.text.split('\n')[0]).join('; ') });
    }

    console.log(`Checked ${ids.length} pages.`);
    if (failures.length > 0) {
      console.error(`${failures.length} page(s) failed:`);
      for (const failure of failures) console.error(`  ${failure.id}: ${failure.reason}`);
      process.exitCode = 1;
    } else {
      console.log('Every page rendered its heading with zero console errors.');
    }
  } finally {
    await browser.close();
    child.kill();
  }
}

main().catch((error) => {
  console.error(error.message);
  process.exitCode = 1;
});
```

## Report only

Per this plan's scope, the following are known, deliberate gaps or behavior changes — not defects to fix now:

- **Standalone pages lose their hand-written multi-source `path` strings.** Today's `CatalogExample.tsx` authors e.g. Colors' `'tokens/palette.ts · tokens/semantic.ts'` or TripPlannerForm's `'Card · InputField · Divider · Button'` directly on the `SectionDef`. The Page API's `path` is always derived (never an authorable field, design §1 "Page shape") — a converted standalone page's Source/Quick-reference line instead shows its own catalog file (e.g. `starter-kit/pages/Colors.catalog.tsx`). This is a 0.1 Page API limitation inherited, not introduced, by this plan (Task 7).
- **The Manifest page is narrower than 0.1's hand-built one.** It now shows generated `components`/`tokens` JSON (props only) instead of every page's `variants`/`states`, because there is no single assembled `sections`/`groups` array left for a standalone page to read, and 0.2 has no `doctor`-style static page reader (that's 0.3) to rebuild one from the scattered page files (Task 7). `buildComponentManifest` itself is kept, exported, unused by the kit — a 0.1 user who built their own manifest view against it is unaffected.
- **`Surface` and `Breathing` stay undocumented.** `native/components/Surface/` has no catalog page today and this plan doesn't add one (nothing in the brief asks for new content, only a faithful conversion of what exists); `Breathing` (a third export of the `Shimmer` folder, alongside `Shimmer` and `SkeletonGroup`) is likewise undocumented today and stays that way. Both simply appear in the kit's sidebar under "Components" with "No examples documented." (`buildCatalogSections`'s existing 0.1 fallback, unchanged).
- **The `useNativeDriver` web warning (Banner) stays report-only.** Carried over from the design's own known-issues list — not a console *error*, and fixing it is explicitly out of this plan's "zero console errors" bar (which only ever covered the two traced bugs, Task 2/3).
- **`shadow*`/`pointerEvents` deprecation warnings (InputField) stay report-only** for the same reason — they're warnings, not errors, and the design's "Starter-kit quality" decision names only the `react-native-svg` errors in `Icon.native`/`Loading` as required fixes for 0.2.
- **Component/token detection heuristics (existing-project `init`) are unchanged from 0.1** — this plan only adds the new-project path; `initExistingProject`'s folder/filename heuristics are exactly what design §2 already called "detection with confirmation."
