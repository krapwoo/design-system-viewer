The one Critical is a small fix, but it must land and be re-verified before the tag.

**Critical**

[Critical] `cli/endpoint.ts:102-131` — "One update at a time" is checked only against `getStatus()`, and the status does not become `updating` until `performUpdate` runs via `setImmediate`, after an awaited `buildPlan()` that takes seconds. Two `POST /update` requests arriving in that window both pass the check, both get 202, and both start `performUpdate`. The panel makes this likely: `UpdatePanel.tsx:271-283` leaves **Update now** enabled with no pending state while the re-plan downloads (2–5 s), so a second click sends a second POST. Result: two concurrent `npm install`s in the same project, two migrates, two restarts. The second `performRestart` removes the first's signal forwarders, waits for a port that is now taken, spawns a `dev` that fails, and `process.exit(1)`s the supervisor, orphaning the first restarted `dev` and its Metro. This violates design §5 and can corrupt `node_modules`. Fix: in `createUpdateEndpoint`, keep a synchronous `let starting = false`; in the `/update` branch, refuse 409 if `starting || phase is updating/restarting`, set `starting = true` before `await deps.buildPlan()`, and reset it on the 502/409 paths (and once `startUpdate` is handed the plan, the status takes over). In the panel, disable the button and show a muted "Starting…" line while the POST is pending. Add an endpoint test that fires two concurrent `POST /update`s and asserts `startUpdate` ran once.

**Important**

[Important] `native/catalog/UpdatePanel.tsx:225-236, 271-283` — A rejected `fetchPlan` or `startUpdate` fetch is unhandled. `planResult` stays `undefined`, so the panel sits on "Checking what this update would change…" forever. This happens whenever the endpoint is unreachable or CORS-blocked: the user opened `http://127.0.0.1:<port>` instead of `localhost` (Origin mismatch, 403 with no CORS header), a Metro-triggered reload lands after the endpoint has closed during the restart, or a stale tab from a previous `dev` run. The mockup's "Can't prepare" state exists for a failed plan request. Fix: wrap `fetchPlan` in try/catch and `setPlanResult({ error: "Couldn't prepare the update. …" })` on failure; do the same for `startUpdate`. Optionally, when the initial `fetchStatus` fails while `update` is non-null, show the same error state rather than "checking".

[Important] `cli/dev.ts:283-287` — When the restarted `dev` exits non-zero, the supervisor prints the recovery command but not the update result. Design §5 restart step 5 requires "the recovery command and the result of the update", and the doctor output was never shown in the terminal at all (it ran in-process), so the user loses it entirely. The `catch` branch at lines 289-291 already prints `handoff.doctorSummary` and `handoff.files`. Fix: print the same "Last known good state" line in the non-zero-exit branch.

[Important] `native/catalog/CatalogShell.tsx:55-67` — The banner's "Migration guide" and "Review update" are `Text role="link"` with `onPress` and no `href`. `CatalogSidebar.tsx:28-32` documents this codebase's own finding that react-native-web only activates `role="link"` on Enter for genuine anchors. "Migration guide" has no keyboard-reachable alternative. Fix: give "Review update" `href={hashForId(UPDATE_PAGE_ID)}` and "Migration guide" `href={releaseUrl}` with `hrefAttrs={{ target: '_blank' }}`, so both render as real `<a>` elements. Also change the banner container from `role="alert"` to `role="status"` as the mockup specifies; a non-urgent notice should not be announced assertively.

**Minor**

[Minor] `cli/updatePlan.ts:95-106` — `defaultGitStatus` returns `undefined` on any git failure, which the plan treats as "outside a git repository" and therefore "nothing is dirty". A `fatal: detected dubious ownership` error, a corrupt repo, or any other non-zero exit disables the dirty check silently and the CLI prints the misleading "(Not a git repository …)" note. Harmless in 0.4 (no migrations; npm rewrites only the version line) but fail-open on the feature's core safeguard. Fix: run `git rev-parse --is-inside-work-tree` first; return `undefined` only for "not a git repository" or ENOENT, and return a plan `{ error }` for other failures.

[Minor] `cli/updatePlan.ts:116, 123, 141-154` — `buildUpdatePlan` runs `npm view`, `npm pack`, `tar`, `migrateEntry`, and `git` with `execFileSync` inside the endpoint's request handler, blocking the event loop for the whole download. `performUpdate` itself is correctly async, but during plan building nothing else in `dev` runs (watcher callbacks, other requests). Fix: switch the `execImpl` default to promisified `execFile` and `await` each call.

[Minor] `cli/updateCheck.ts:68-73, 129-130` — `checkForUpdate` is documented as never throwing, but `parseVersion` throws on a non-semver `latest` from a parseable cache or an unexpected 200 body without `version`. Because `dev()` awaits `refreshUpdateFile` first, that throw stops `dev` from starting. Fix: wrap the body of `checkForUpdate` in try/catch returning `undefined`.

[Minor] `cli/update.ts:93` — The doctor step is not wrapped in try/catch. A doctor crash rejects `runUpdate`, and `main` prints only the raw error, losing the "installed and migrated successfully" context. [Minor] `cli/dev.ts:150-152`, `cli/update.ts:77`, `cli/updatePlan.ts:123, 141` — `execFile('npm' | 'pnpm' | 'yarn' | 'tar', …)` without `shell` cannot run the `.cmd` shims on Windows. The Expo spawn already uses `shell: process.platform === 'win32'`. [Minor] `cli/dev.ts:250-255` — Between `removeAllListeners` and `targetChild = newChild` (up to about 15 s worst case), SIGINT and SIGTERM are swallowed: `forward` is a no-op and the restart proceeds, so Ctrl-C in that window brings the viewer back up instead of stopping it. Fix: if a signal arrives while `targetChild` is undefined, set a flag and skip the spawn, exiting 0 after the old child is gone.

[Minor] `cli/dev.ts:338, 402-407` — `void performUpdate(...)` has no `.catch`. A throw outside the guarded steps (for example `writeFileSync(statusFile)` failing) becomes an unhandled rejection that crashes `dev`. With Expo now spawned `detached: true`, any `dev` crash leaves Metro bound to the port with no terminal to send it SIGHUP. Fix: add `.catch` that records a `failure` status, and add `process.on('uncaughtException' | 'unhandledRejection')` that kills the Expo group before exiting.

[Minor] `cli/workspace.ts:76` — The secret is baked into `entry.tsx`, which Metro bundles. The Host and Origin checks make the leaked secret unusable from a browser, and a local non-browser process is outside the threat model, so this is informational and consistent with design §5 ("writes it into the generated viewer files"). No change required; worth a sentence in the README's safeguards paragraph so the layered model is explicit.

[Minor] `cli/dev.ts:169` and `native/catalog/UpdatePanel.tsx:158` — `doctorSummary` is the full stdout of `doctor` (every issue plus Fix lines). [Minor] Tests — `cli/__tests__/endpoint.test.ts:71-78` tests a wrong secret of a different length, so the `timingSafeEqual` call is never reached (the length check short-circuits); add a same-length wrong secret. `cli/__tests__/dev.test.ts:141-160` asserts install was called but not the install → migrate → doctor order that `update.test.ts:95` does assert. `cli/__tests__/updatePlan.test.ts` always injects `gitStatusImpl`, so `defaultGitStatus`, `stripRepoPrefix` and Errata 6's pathspec handling have no unit coverage; exporting `stripRepoPrefix` would make it testable in one assertion.

**What is solid**

- The endpoint's check order (Host → Origin incl. preflight → missing Origin → `timingSafeEqual` secret → route) matches §5 exactly. Error responses carry no CORS header, success responses echo only the exact allowed origin, request bodies are never read, state changes are POST-only, and the dirty refusal is authoritative server-side with no override path. A form POST, `<img>`, or DNS-rebound page cannot pass; a second `dev` on another port cannot cross over.
- The secret never reaches logs, `update-status.json`, or error bodies. `.ds-viewer/` is gitignored by `init`.
- `performUpdate` is fully async, reports a correct three-state step list, and writes the status file before `performRestart`. The file is read once and deleted. Errata 7a–7e are all implemented as specified, and the `findFreePort` probe fixes the `[::1]` issue the spike found. The old `child.on('exit')` running during the restart is harmless (double `close()` is safe).
- `buildUpdatePlan` writes only in a `mkdtemp` folder, cleaned in `finally` on every path. Nothing writes to a kit file anywhere; `MIGRATIONS` is empty and asserted empty. Rename handling and subfolder prefix stripping in porcelain parsing are correct. Lockfile detection and the per-manager upgrade command are right for npm, pnpm, yarn classic and berry.
- The viewer renders all ten mockup states with the right structure and copy (U+2019 throughout), the footer link is a real anchor with `aria-current`, dismissal is per version in `localStorage`, Back works through the hash history, heading focus follows `SectionBlock`'s pattern, and Errata 1 and 2 are correctly implemented including the "one failed probe first" reload guard.
- The update check holds only `latest`/`summary`/`releasedAt`/`checkedAt` in a shared cache, recomputes `current`/`breaking` per project, never regresses the cache, times out at 900 ms per request, is silent offline, honours both opt-outs, and never runs with `--ci`.
- Tests are real behavioural tests over a loopback socket with injected effects, and the controller confirmed no network and no `npm` calls during `npm test`.
