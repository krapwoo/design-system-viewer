## Decisions (do not reinvent)
1. **Update check** (design §5): in `dev` and `doctor` only, never with `--ci`; at most once per 24 h, cached in the user's cache folder (macOS `~/Library/Caches/ds-viewer`, Linux `$XDG_CACHE_HOME` or `~/.cache`, Windows `%LOCALAPPDATA%`), shared across projects; `GET https://registry.npmjs.org/@krapwoo%2Fds-viewer/latest` and the GitHub release for that tag (summary), each with a timeout under 1 s; silent when offline; disabled by `updateCheck: false` or `DS_VIEWER_NO_UPDATE_CHECK=1`. `dev` writes `.ds-viewer/update.json`; the viewer reads it through generated data; the browser never contacts the network for updates. `doctor --json` fills `update` (`{ current, latest, breaking }`) from the cache or check.
2. **Viewer:** footer line (minor/patch and major), major banner dismissible per version (stored in `localStorage` keyed by version), and the Update page at `#ds-viewer-update`, matching the approved mockup. Back returns to the previous page. After the restart, the browser reloads the same address and the page shows the recorded result.
3. **Local endpoint** (design §5 safeguards, all of them): `127.0.0.1`, random port, per-`dev` secret written into generated viewer files and sent in a request header, exact `Origin` match (including port) on every request including CORS preflight; requests without `Origin` rejected; state changes POST only; endpoints `POST /plan`, `POST /update`, `GET /update/status`; one update at a time; refuses with the plan's dirty-file list (no override in the viewer). Handle CORS preflight (`OPTIONS`) correctly for the custom header, only for the exact origin. Tests for every rejection path.
4. **Update plan, `update`, `migrate`:** exactly design §5. Package manager detected from the lockfile (reuse the detection in `cli/githubAction.ts`). Dirty-file detection via `git status --porcelain` limited to planned files; outside a git repository, say so and treat files as not dirty (state this in the plan and README). `update --force` overrides dirty files in the CLI only.
5. **Migrations framework:** a registry of migrations keyed by the version that introduced them; `migrate --from <v> [--dry-run] [--json]` runs every migration after `<v>`; each migration declares the files it would change and is idempotent; before/after fixture tests. 0.4 has no breaking change, so it ships an empty production registry plus a test-only sample migration in fixtures. State this in the release notes.
6. **`kit diff <Component>`:** compares the user's kit file(s) with the installed package's `starter-kit/` copy and prints a unified diff. Kit root: add optional `starterKit.root` (written by `init --new`, default `src/ds`); when absent (0.2/0.3 configs), infer it from the components glob. `update` reports "N kit files differ from the installed kit's version".
7. **Restart handoff:** exactly design §5 steps 1–5, including pausing the watcher and hot reload during an endpoint update and restarting on the same Metro port.
8. **End-to-end proof before release:** the full **Update now** flow must be exercised against a real newer package without publishing, for example a local npm registry (Verdaccio) or a packed tarball. Choose by spike, prefer no production test hooks, and if one is unavoidable keep it env-gated, undocumented and refused when `--ci` is set. Put it in the controller verification task.
9. **Not workers' work:** publish, tags, commits. Commit steps marked "(only with commit authority)".
10. **Release notes** per user-visible change; a README section for updating, `migrate` and `kit diff`.
