`doctor --render` starts its own `dev` server with the new `--no-update-endpoint` flag, so it no longer creates a local update endpoint. Both servers share one generated `.ds-viewer/` workspace, and the check used to write its own short-lived endpoint into it — which left an already-open catalog calling a port that died with the check, reported on the update page as "Couldn't reach the viewer's local server. If this keeps happening, restart npx ds-viewer dev." Now the check leaves no endpoint behind: the open catalog's update page shows its status without its actions until `dev` is restarted, instead of failing against a dead port.

`startDev` also waits for the catalog to answer before the first navigation. It resolved as soon as `dev` printed the port, which `dev` does before it spawns Expo, so the first page load raced the bundler.

A refusal the page is allowed to read — a wrong secret (401) or an unknown route (404), where the Origin check has already passed — now carries the `Access-Control-Allow-Origin` header. Without it the browser blocked the response and the update page could not tell a wrong secret from a server that was not running: both arrived as the same opaque network failure. A rejected or absent Origin still gets no CORS headers at all.
